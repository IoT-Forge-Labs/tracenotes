How a ticket reaches main in tracenotes, and every gate on the way
1

Ticket

tickets/T-NNN.md + a GitHub issue with acceptance criteria

2

Investigation gate

Every claim the ticket makes about the code is checked first (Qodo Codebase Wisdom or a command). A wrong claim rewrites the ticket.

I decide
Read the revised ticket, pick the lane: agent session or bot
3

Build test-first

Red test kept as evidence, then npm run check: typecheck + 357 tests

4

Qodo local review (deep)

Every valid High and Medium fixed test-first. At most 3 rounds, then stop: NOT MET.

I decide
Every Low, every disputed finding, what a stop means
5

Pull request, enforced by GitHub

check on Linux and Windows, ticket-link (Closes #N), actions pinned to commit SHAs

6

Qodo PR review → workflow

No Medium+ finding on the head → label “Qodo approved”. A label, not an approval.

Guarded: a person reads it
.github/workflows/** and scripts/**, where the gates live
7

I merge

After the gate report says MET. GitHub closes the issue.

Planned, not built: Qodo review on the bot lane in a job that never runs ticket-written code (T-029) · an MCP server so agents can use the app (T-013).
Known gap: gate 6 is procedure — GitHub doesn’t enforce it, my gate report does.
What Qodo caught
I wrote a check that every GitHub Action is pinned to a commit SHA, as regexes over YAML. Seven Qodo reviews found eight ways past it, one at a time. The fix that held: GitHub’s own sha_pinning_required. My test is now the early warning.
Lesson
Read back any setting that lives outside the repo. My approval guard lost its path on the first save and quietly became “whole repository”. The screen looked right.
